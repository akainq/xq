Projects

A project is a directory with an xq.toml file: its name and version, the XQ version it needs, its programs, its tests and the packages it uses. Without a file argument, the commands xq build, xq run, xq check and xq test work on the project the current directory is in: the nearest directory with an xq.toml up the tree. Given a file, they work on that one file, as without a project.

#xq.toml

[package]
name = "chat"
version = "0.1.0"
xq = "0.10"             # the XQ version the project is written for

[[bin]]                 # a program of the project; there can be several
name = "server"
main = "server.xq"

[[bin]]
name = "client"
main = "client.xq"
gui = true              # a GUI program (like `xq build --gui`)

[test]
dir = "tests"           # where the tests are (this is also the default)
  • name consists of lowercase ASCII letters, digits, - and _; version is three numbers.
  • xq is the XQ version the project is written for: 0.10 means any 0.10.x, and 0.10.2 means 0.10.2 or newer within 0.10. Before 1.0, a change in the second number counts as incompatible; from 1.0 on, a change in the first: 1.2 accepts 1.2 and newer, up to 2.0. A compiler of a different version refuses to build the project and says which version it was written for.
  • Without [[bin]] there is one program: main.xq in the project root, named after the project.
  • An unknown key is an error that lists the known keys: a typo does not slip through silently.

The file is TOML. The parser handles the part of TOML that manifests use: tables and arrays of tables, keys (dotted ones too), strings in "…" and '…', integers, true and false, arrays (multi-line ones too), inline tables {…}, # comments. There are no multi-line strings, floats or dates: the error says so and gives the line.

#Commands

CommandWhat it does
xq new namecreates a project in directory name: a program (main.xq and a module it imports) with a test; --lib makes a package (lib.xq)
xq buildbuilds all the project's programs into target/release/ (with -g, into target/debug/)
xq build serverbuilds one program; -o path writes it to that file
xq run [program] [-- args]builds and runs a program (the name can be omitted if there is only one)
xq checktype-checks the project's programs and tests
xq test [filter]builds and runs the project's tests (those whose names contain the filter)
xq test path…the tests in these directories and files, inside a project or outside one

Imports work as in a single file: your own modules by relative path (./lib/greet), standard ones as std/…; packages by name (below).

#Packages

A package is a project whose modules other projects import. Its module for import "name" is lib.xq at the root of the project, or the one named in [lib]; import "name/x" is the module x next to it. xq new name --lib makes a new one.

[package]
name = "qr"
version = "1.2.0"
xq = "0.10"
description = "QR codes"                      # the description, address and license are for the registry
repository = "https://github.com/someone/qr"
license = "MIT"

[lib]
main = "src/qr.xq"                            # lib.xq by default

[dependencies]
util = "1.1"                                                      # from the registry
img = { git = "https://github.com/someone/img", tag = "v0.3.0" }  # from git (or rev = "commit")
draft = { path = "../draft" }                                     # from a directory

A project uses the packages of its [dependencies] and imports them by name:

import { encode } from "qr";
import { Matrix } from "qr/matrix";

A module can import only what its own project depends on: the dependencies of package qr are its own, not the project's. Packages are compiled together with the program, like its own modules.

#Versions

"1.2" means version 1.2.0 or newer in the same line, "1.2.3" means 1.2.3 or newer. A line is a set of versions compatible with each other: from 1.0 on, the first number holds them together (1.x); before 1.0, the second one (0.4.x). A program has one version of each package: the smallest one that everyone asking for it accepts (minimal version selection, as in Go). Newer versions never come by themselves, only when asked for (xq update). Asking for different lines (1.x and 2.x) is an error, and the error says who asks for what.

The choice is written to xq.lock, as exact commits; commit it. As long as xq.toml asks for the same, builds take the versions from there and do not touch the network.

CommandWhat it does
xq add qradds a package of the registry to [dependencies] (its newest version) and fetches it
xq add qr 1.1the same, with this version
xq update [packages…]asks for the newest versions in their lines (of all packages, or of those named) and chooses again
xq fetchchooses the versions and fetches the packages (build, run, check and test do it themselves)
--offline (or XQ_OFFLINE=1)fetches nothing: everything needed is in the cache already

Packages are fetched with git, which must be in PATH. The repositories are kept in the cache, ~/.xq (or XQ_HOME), and the files of each version in its pkg/.

#The registry

The package registry is akainq/xq-packages, with a searchable site at akainq.github.io/xq-packages. A package of the registry is a git repository with tags vX.Y.Z. To add one, open a pull request with a file packages/name.toml; a new version is a new tag: the registry's robot reads the tags and builds the index (the branch index) with the versions, their commits and dependencies. A version that made it into the index never changes, even if its tag is moved.

A package of the registry depends only on packages of the registry. XQ_REGISTRY names another registry: a git repository with the index on branch index, or a directory with the index.

#Tests

A test is a program name.xq in the tests directory or its subdirectories (except lib, which holds modules that the tests import, and C files: lib/name.c is built into a dynamic library name for tests that call C — declare library "name" and // needs: library name). A test passes if the program prints exactly what is in name.out, exits with code 0 and does not leak memory: the runtime counts it as each process exits (XQ_CHECK_LEAKS=1). A name.in next to the test is fed to its standard input. Lines at the start of a test say more:

LineMeaning
// needs: library opus (or // needs: opus)the test loads this dynamic library; without it, the test is skipped
// needs: program nodethe test runs this program from PATH; without it, the test is skipped
// needs: gputhe test draws (std/gpu); without a Vulkan loader (MoltenVK on macOS), it is skipped
// needs: env XQ_TEST_PGthe test takes the address of a server (a database) from this environment variable; without it, the test is skipped
// alonethe test measures time and runs while no other test is building or running
// exit: 3the code the program must exit with
// env: NAME=valuean environment variable for the program

Tests run in parallel, as many at a time as there are cores (-j N runs N at a time), from the project root: they read files by paths relative to it. They are built with -O1 (it builds faster; -O2 and other levels are set with a flag). With -g, they are built with debug information and without optimizations: what is kept for the debugger must change neither the output nor the memory that gets freed. At the end, xq test shows what did not match and how many tests passed, failed and were skipped; the exit code is 1 if anything failed.
